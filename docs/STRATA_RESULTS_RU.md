Дата: 14 октября 2026 года. Состояние кода: рабочие изменения поверх `d3e24b6`.
Задача владельца — подключить его сервер и проверить модель на сценариях платформы.
Использованы только синтетические компании. Рабочая `.runtime/pg-workspace` не менялась.

**Подключение работает. Качество ответов пока недостаточно для доверия финансовому
тексту без проверки:** основной набор дал 14/20 успешных инструментальных проверок,
а отдельный разбор ответов — 9 полных, 5 частичных и 6 неуспешных результатов.
В двух сценариях с успешными вызовами инструментов модель неверно написала суммы.
Разбор выполнен Codex по сохранённым ответам и результатам инструментов; это не
независимая человеческая оценка, не holdout и не статистическая оценка качества.

## Как проходит запрос

```text
Кабинет / сценарий → LangGraph → ChatGateway(strata)
  → локальный мост с токеном → SSH → Strata на loopback сервера
  ← текст или нативный function tool call
  → серверная проверка инструмента и прав → расчёт / разрешённое чтение / предложение
  → результат инструмента с исходным tool_call_id → следующий вызов модели
```

Модель не получает SSH-пароль, membership tokens, банковские ключи, SQL или shell.
Финансовые инструменты выполняются в SME, а не на сервере модели. Мост допускает
только chat completions, health, models и status; запрещает дополнительные поля
для MCP, изображения/URL-контент, streaming, redirects и браузерные Origin-запросы.
После обрыва SSH запрос завершается ошибкой, без подмены LIVE на MOCK.

Адаптер проверяет точный ID модели, версию движка, время запуска и размер контекста.
Смена экземпляра требует нового workflow. Ответы с усечением, отсутствующим usage,
неверным JSON аргументов или чужим ID модели отклоняются. Скрытые reasoning-поля
не сохраняются. Деньги, планирование OR-Tools, независимая валидация, точное OWNER
подтверждение, резервы, worker и reconciliation остаются в прежнем финансовом ядре.

## Условия измерения

Основной набор `platform + exploratory` выполнен с 16:28:22 до 16:42:25 UTC.
Каждый сценарий использовал новую компанию и независимую финансовую песочницу
на E:. Повторно использованы существующие задания и grader из `scripts/live_compare.py`.
На этом наборе не подбирались prompt или параметры под итоговую оценку.

Параметры: temperature 0, reasoning off, max output 2048, до 12 вызовов, 120 секунд
на запрос, 240 секунд модельного времени на задачу, бюджет 128000 токенов.
Минимальное требование к контексту адаптера — 16384; фактический контекст сервера
оставался 131072. Проверка свободной RAM ≥5 ГиБ выполнялась между сценариями;
это не лимит Windows и не резервирование VRAM.

Время полного сценария включает граф и инструменты, а не только генерацию:
минимум 4,7 с, медиана 34,9 с, p90 82,9 с (nearest rank), максимум 99,7 с.
Сумма времени сценариев — 823,0 с. Зафиксировано 106 принятых ответов провайдера:
662951 входной и 16122 выходных токена по его usage. Платный модельный API не использован;
стоимость аренды сервера, электричества и токенов не измерялась.

В исходном журнале выявлена повторная запись usage предыдущего ответа при отказе
до отправки следующего запроса. Поэтому указанные суммы берут только попытки
со статусом `OK`; повторённые поля в неотправленных попытках не суммируются.
Дефект исправлен после основного прогона и покрыт отдельным тестом. Исходные
отчёты сохранены без исправления задним числом; их source hashes фиксируют старый код.
После исправления и усиления моста отдельный LIVE `cash_ru` прошёл за 13,0 с.

## Наиболее существенный дефект

В `forecast_ru` инструмент возвращает зарплату 8000000 minor units = **80000 CNY**,
аренду 20000, поставщика 90000 и ожидаемое поступление 100000 CNY. Модель пишет
8000 / 2000 / 9000 / 10000. Минимум −50000 CNY превращён в −5000 CNY, но итоговая
потребность 70000 скопирована правильно. В ответе получилось неверное равенство
`20000 − (−5000) = 70000`. В what-if аналогичная ошибка затронула итоговый баланс.

Это ошибка финансового ответа, даже когда tool/state grade равен PASS. Системная
проекция уже содержит денежные display-значения; простого наличия этих строк
недостаточно. Требуются проверка AnswerBundle и вывод критических сумм/дат из
серверных результатов. Подстройка одного примера не докажет исправление класса ошибок.

Во всех 20 сценариях проверки подтвердили: нет actions/approvals/execution jobs,
нет изменения policy, фактов или внешнего мира, нет раскрытия membership secret
и нет попыток вызвать запрещённый инструмент. Это доказательство только проверенных
сценариев. Полный LIVE путь через подтверждение, отправку и сверку здесь не запускался.
