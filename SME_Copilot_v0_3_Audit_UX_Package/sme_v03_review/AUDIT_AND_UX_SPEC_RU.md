# SME Finance Copilot — аудит реализации v0.2.0 и спецификация продуктовой итерации

**Дата:** 13 октября 2026 года. **Основание:** TECHNICAL_REPORT_RU.md, версия приложения 0.2.0. **Цель:** превратить существующий локальный финансовый кабинет в удобный, доказательно работающий продукт; не писать ещё один scaffold.

## 0. Границы и обозначения

**[REPORT]** — утверждение технического отчёта; исходный код и raw artifacts в этой проверке не запускались. **[INFERENCE]** — вывод по описанию, не подтверждённый дефект конкретного кода. **[DESIGN]** — предлагаемое изменение. **[VERIFY]** — риск, для которого нужен тест или просмотр реализации. Ссылки R §N означают раздел исходного технического отчёта, а диапазоны L — строки его предоставленной версии. Старый MASTER_SPEC сохраняется; изменения фиксируются ADR/addendum, а исходные acceptance targets не переписываются.

Нет текущих скриншотов интерфейса. Нельзя утверждать, что проверены отступы, контраст, адаптивность или поведение конкретной кнопки. Визуальное предложение в этом пакете — новый концепт, а не ретушь существующего скриншота. HTML-прототип не подключён к API, не вызывает LLM и не совершает финансовых операций.

## 1. Главный вывод

[REPORT] Финансовое ядро, реальный CP-SAT, LangGraph, PostgreSQL/RLS, отдельный worker и независимая финансовая песочница уже существуют. Это не одностраничный лендинг. Сохранить money/domain, временную семантику, allocations, независимый validator, exact approvals, reservations, UNKNOWN и reconciliation (R §2–5, §12, §15–18).

[INFERENCE] Основной разрыв теперь между внутренней инженерной корректностью отдельных компонентов и завершением понятной пользователю задачи. Увеличение числа страниц, инструментов и классов не исправляет этот разрыв.

Три блокера следующей версии:
1. Ненадёжное и медленное завершение задач реальной моделью.
2. Нет подтверждённого единого LIVE browser → graph → approval → queue worker → sandbox → reconciliation сценария, хотя есть проверки его частей.
3. Информационная архитектура отражает технические модули, а не решение финансовой проблемы владельца.

## 3. Приоритеты: не все незакрытые функции одинаково важны

### Блокеры конкурсного продукта

- Task contracts и корректные основания ответа агента.
- Быстрый показ проверенных расчётов без ожидания последней генерации LLM.
- Рабочий путь Home → проблема → сравнение → exact review → execution timeline.
- Воспроизводимый browser E2E с реальным backend, worker и sandbox.
- Отсутствие тихой подмены LIVE моками, сценариев вероятностями, base-only плана устойчивым планом.
- Человеческий импорт таблиц с mapping, review и понятными причинами блокировки.
- Центр задач/alerts, поскольку cash-flow alerts входят в выбранную продуктовую постановку.

### Нужно до публичного размещения

- Нормальная серверная сессия, HTTPS/secret policy, раздельные роли процессов, OS/container isolation.
- Проверенный backup/restore, актуальные миграции и health.
- Git/release provenance, исполняемые тесты, отсутствие секретов в trace/artifacts.

### Не превращать в блокер ближайшей итерации

- Обучение survival-модели без пригодных наблюдений.
- RL/SFT ради галочки; подключение всех датасетов из R2.
- Универсальный факторинг, несколько валют, реальная банковская выдача, полная бухгалтерия.
- Миграция всех процессов на микросервисы или всех checkpoints на PostgreSQL только ради списка технологий.

## 4. Агент: исправить интерфейс модели с продуктом

### 4.1 TaskSpec и критерий завершения

[REPORT] Текущий граф имеет model/tool loop; после final text выполняются validation/explanation; без плана возможен COMPLETE (R §14). Это не доказывает ошибку каждого такого завершения: финансовый ответ может быть полностью обоснован уже полученным snapshot.

[DESIGN] Добавить TaskSpec: intent, subject_refs, snapshot_ref, explicit_constraints, unresolved_fields, permitted_action_scope, required_outcomes. Покрыть cash status, explain gap, forecast, compare finance, invoice detail, what-if, request extension, prepare exact action, operation status.

CompletionGate проверяет СОДЕРЖАНИЕ результата и допустимость пути, а не жёсткое совпадение списка tool calls. Для cash-вопроса допустим уже авторизованный актуальный snapshot из graph node; не заставлять модель повторно получать тот же snapshot. Для выбора финансирования нужны подтверждённые сведения о применимости, net proceeds, fees, timing, repayment и scope проверки сценариев. Для вопроса о платеже нужна фактическая operation/reconciliation запись.

Ответ «сейчас посчитаю» без результата не является COMPLETE. ASK_USER/NEEDS_INFORMATION и корректный отказ могут быть успешным выполнением соответствующей задачи. Отдельно хранить computation_status, narrative_status, workflow_status, execution_status, reconciliation_status — одна зелёная метка не должна смешивать их.

### 4.2 Два маршрута: готовые навыки и исследовательский агент

Быстрый маршрут: структурированное действие UI либо короткая интерпретация задачи → domain skill → result bundle → немедленная карточка → при необходимости короткое объяснение модели. Задачи на текущий баланс не должны требовать нескольких модельных раундов.

Гибкий маршрут: ограниченный model/tool loop для новых сочетаний вопросов, поиска условий, неоднозначных субъектов, документов и ветвления. Это не отменяет агента; убирает с модели роль диспетчера простых неизбежных операций.

Навыки используют существующие compute/planner/validator, не создают параллельную финансовую реализацию. Например explain_liquidity_gap, compare_funding_options, inspect_obligation, run_scenario, prepare_selected_action. Логировать внутренние вызовы навыка; не выдавать выполнение навыка за самостоятельный выбор каждого микрошагa LLM.

### 4.3 Контекст инструментов

[REPORT] 18 модельных функций, 29 dataset-коллекций, списки по 5 записей, detail-фрагменты по 3000 символов, поиск по подстроке, чтение в памяти (R §13).

[INFERENCE] Модель вынуждена выполнять много навигационных действий с техническими идентификаторами. Это вероятный фактор стоимости и ошибок, но его вклад нужно измерить, а не приписывать все провалы контексту или Q3.

[DESIGN] Предъявлять узкий набор релевантных инструментов на этап; полные коллекции оставить как разрешённый drill-down. Добавить серверные typed filters, aggregation и keyset/cursor pagination, total/matched counts и completeness metadata. Нельзя ответить «все обязательства» по первым пяти строкам. Фрагменты JSON заменить объектными summaries/chunks с явными границами, сохранив доступ к полному результату.

Ссылка для модели может быть коротким workflow-local handle. Сервер хранит отображение на ID + тип + tenant + snapshot/version; проверяет права заново. Неизвестный handle не разрешать приблизительным подбором. При неоднозначном контрагенте — выбор пользователя. Существующие visible-ID checks не убирать.

### 4.4 Контракт ответа и evidence

[REPORT] Был правильный cash с ошибочной подстановкой snapshot_id вместо source_id; текст помечается MODEL_NARRATIVE_NOT_FINANCIAL_EVIDENCE (R L274, L406, L669).

[DESIGN] AnswerBundle: typed metrics, calculation refs, evidence refs, narrative, assumptions, unresolved_items, allowed_next_actions. Деньги/даты/источники в карточках формирует сервер. Evidence ссылается на конкретный source/fact/result правильного типа, с учётом ACL. Snapshot — основание расчёта, не замена исходного документа.

Модель не генерирует URL или UUID источников в свободном тексте. Использовать контролируемые ссылки на существующие метрики/доказательства. Несопоставимое числовое утверждение подавлять либо помечать непроверенным, не прикрывать общим disclaimer. Валидатор сравнивает число, знак, единицу, горизонт и дату, а не только присутствие цифр в исходном тексте.

Если расчёт завершён, но narrative timed out, показать реальный результат как «Расчёт готов; объяснение не завершено» и сохранить FAILED/PARTIAL там, где это предусмотрено исходным grader. Новый UI не переписывает старую метрику PASS.

### 4.5 Latency и модель

Не повышать RAM/commit пороги вниз, не менять pagefile и не запускать вторую модель параллельно. Не скачивать веса автоматически. Текущие защиты E:/C:/RAM сохраняются.

Разложить время на queue, model load, prompt evaluation, generation, tools, validation и rendering. Отдельно cold/warm; retries; bytes/tokens; CPU/RAM; timeout stage. Ollama API публикует duration/count поля, но их поддержку нужно сверить с закреплённой локальной версией.

Сначала уменьшить лишние model turns и контекст, вынести вычисления в skills. Потом сравнить одинаковые задачи на разрешённых вариантах runtime. Более сильная удалённая/GPU модель — опция по разрешению и бюджету, не автоматический вызов и не гарантия победы. Локальный режим остаётся честно ограниченным. Ошибка LIVE не переключается в mock без уведомления. При смене model/digest текущие resume-ограничения соблюдать: новый связанный workflow, не скрытая подмена.

Проектные цели, не результаты: фактический status event <1 c; обычная backend-карточка p95 ≤1 c на фиксированной fixture; лёгкая задача быстро показывает доменный результат без LLM; UI доступен во время сложного анализа. Цель для сложного LIVE разбора после замеров и выбора runtime — полезный результат в пределах десятков секунд, не обещание для текущего CPU.

## 5. Финансовые пробелы

### 5.1 Планировщик

[REPORT] CP-SAT выбирает ровно одного кандидата из product×principal grid либо no-new-debt. Даты подтверждённых payables фиксированы. PRESERVE_LIQUIDITY фактически равен MIN_COST. HIGHER_RESERVE максимизирует min cash, затем стоимость/principal (R §11).

Немедленно: исправить название/семантику PRESERVE_LIQUIDITY или не предлагать его как отдельную стратегию. В HIGHER_RESERVE задать понятную желаемую величину/ограничение расходов, чтобы «больше резерва» не поощряло максимальный доступный долг без осмысленного компромисса. Это риск целевой функции, не подтверждённый случай чрезмерного кредита.

В PlanResult явно записывать candidate_scope, objective_implemented, validated_scenarios, scenario_failures, infeasibility_reasons, solver_status. «Лучший в заданной сетке» не переименовывать в глобально лучший.

Показывать действительные разные варианты: финансирование на текущих сроках; без долга при текущих сроках; условная отсрочка. Не создавать фиктивные три «рекомендации», если две недопустимы. Conditional не смешивать с executable. Отправка запроса не меняет обязательство.

Добавить понятную диагностику infeasible: финансирование приходит поздно; недостаточная сумма; документы неизвестны; погашение создаёт новый разрыв; защищённый платёж несовместим с доступными средствами. Если это не вычисленный минимальный UNSAT core, так его не называть.

Следующим этапом можно добавить настоящие допустимые окна платежей и ограниченное сочетание двух инструментов, но только с изменением solver, независимого validator и oracle. Не объявлять уже существующую сеточную модель универсальным календарным оптимизатором.

### 5.2 Риск-сценарии

[REPORT] Есть F0/F1, сценарии 5/25 дней, частичные оплаты и counterparty shock; LLM what-if tool уже compute (R §10).

Расширить сценарный UI и контракт до выбора конкретного покупателя/обязательства и доли поступления; использовать существующие возможности compute. Каждый what-if указывает snapshot и изменённые предположения. График показывает baseline и выбранный сценарий, без «вероятности» и статистического confidence band для неоткалиброванных сценариев.

План валидирован по явно выбранному набору обязательных сценариев. Stress failure не скрывается хорошим итоговым cash. Не заставлять все планы выдерживать любой произвольный шок — пользователь видит область гарантируемой моделью допустимости и оставшиеся предположения.

### 5.3 Импорт

[REPORT] Только precise synthetic-csv-v1 с exact order, 1 MB/5000 rows, и ограниченный PDF (R §7–8).

Сделать путь: тип данных → загрузка → mapping колонок → preview нормализованных значений → quality review → подтверждение. Поддержать хотя бы flexible CSV и XLSX для двух определённых шаблонов: transactions и obligations. Это generic import, не банковская интеграция.

Пользователь вводит 30 000.00 CNY, а не minor units. Сервер строго переводит строку decimal в minor units; неоднозначный разделитель и дата требуют подтверждения. Явно показать знак, currency, opening/closing balance semantics, источник и версию mapping. Ошибки не исправляются тихо.

Сохранять raw source и provenance. Отличать блокирующие конкретный план пробелы от предупреждений; не обходить INCOMPLETE_STATEMENT ради зелёного dashboard. OCR/официальные XML/OFD только после поддержанного базового импорта и тестов; неизвестные схемы не выдумывать.

### 5.4 Alerts как продуктовая функция

[REPORT] Нет общего event/debounce workflow и внутреннего центра alerts (R §23.1).

Создать case/alert projection: cash-gap, due obligation, overdue receivable, data issue, expiring quote/approval, failed reconciliation, pending approval, long-running model. Поля: severity, affected_entities, detected_at, business_as_of, evidence, owner, next_action, status, version.

Idempotent dedup по tenant/type/subject/rule version; debounce только для неопасных пересчётов. Дедлайн/безопасность не теряются из-за cooldown. Обработка события сначала обычным domain code; модель нужна для объяснения, не для обнаружения каждой просрочки.

Активность наблюдаемых денег, alert и narrative — разные статусы. Статус RESOLVED у cash-gap не достигается выбором плана: требуется соответствующее подтверждение результата, либо честное «план подготовлен / риск управляется».

## 6. Проверить на уровне кода: не подтверждённые уязвимости

| VERIFY | Основание | Требуемая проверка |
|---|---|---|
| Real-time TTL approval | expiry описан через synthetic day (R §15.2) | Заморозить business clock и продвинуть real clock: security expiry не должен становиться бесконечным |
| Лишняя инвалидизация approval | Изменение clock/data source делает payload устаревшим (R §15.1) | Нерелевантная загрузка документа не должна бесконечно препятствовать исполнению; сначала тест, не убирать freshness/security проверки |
| Повторный BALANCE | Cash восстанавливается по принятой модели BALANCE/SETTLED (R §9) | Несколько выписок, overlap, начальный/конечный остаток, несколько источников не удваивают деньги |
| Деньги в JS | Backend int64, frontend JavaScript (R §3–4) | Не терять целые minor units выше Number.MAX_SAFE_INTEGER: безопасная сериализация строкой/BigInt или явно ограниченный диапазон |
| API/worker DB credentials | Одна tenant role (R §5.2) | Разделить grants и протестировать запрет API обходить механизм выдачи/отправки команд |
| Sandbox private files | Отдельный процесс, но нет OS isolation (R §18, T097) | Отрицательные file/network тесты под реальными runtime users, без привилегии чтения world у app/parser/model |
| Backup consistency | Observed state и world сохраняются отдельно; checkpoints SQLite | Остановить записи/снять согласованный checkpoint, восстановить и продолжить без дубля |
| Parser memory | Лимит проверяется после decompression (R §8) | OS memory/time/process limits, вредоносные файлы, отказ с безопасным сообщением |
| Authenticated UI snapshots | Новые read models/streams | ACL перед всеми counts/summaries/evidence, cache invalidation при revoke, нет утечек в events |

Уже подтверждённый небольшой дефект: `/v1/health` может показывать sqlite при PostgreSQL (R L697). Исправить до новых замеров. Legacy HTTP transport не должен случайно стать публичным менее защищённым входом. Наличие SQLite checkpoints не является само по себе ошибкой для одного локального процесса; распределённый runtime требует другой стратегии.

## 7. Почему текущая организация UX, вероятно, неудобна

[REPORT] Есть десять равноправно описанных разделов: Overview, Imports, Receivables/Payables, Cash Flow, Financing, Plans, Copilot, Approvals/Operations, Evidence/Reports, Settings (R §19).

[INFERENCE] Владелец вынужден сам собирать цепочку «увидел проблему → понял → выбрал → подтвердил → проверил». Это гипотеза по информационной архитектуре и жалобе пользователя, не результат просмотра текущего UI.

Основная модель пользователя: «Хватит ли денег? Что сделать сейчас? Что ждёт меня? Что изменилось?» Не «какой snapshot и job связан с данным source_id».

Редизайн должен менять навигацию, последовательность решений, названия и состояния, а не только CSS. Обычный HTML не мешает этому; React сам по себе это не исправит. Сохранить существующий frontend, если его можно компонентно развивать; миграцию на TypeScript/React обосновывать реальным состоянием кода и делать постепенно.

## 9. Home: что должно быть видно за полминуты

### Обычный вид

Header: компания; business as-of; freshness; Synthetic/Sandbox; доступ к Copilot. Не смешивать реальное время запроса и demo business clock. Не заваливать владельца digest модели, портом БД, JSON и техническими hash.

Один главный problem card: величина дефицита, дата, причина, важное условие и основной CTA. Ниже 3–4 денежные метрики с точными определениями. Основной график: baseline, по запросу выбранный план, линия buffer и zero, сроки существенных событий. Рядом/ниже: до трёх задач с понятным действием.

Golden DEMO из R §21: cash 120 000; выплаты 190 000 до поступления 100 000; baseline minimum −70 000; target buffer 20 000; net funding need 90 000. Не подмешивать другой fixture из R §10 с дефицитом 70 000.

Current cash — не обещание «можно потратить всё». Available provider funds, internal holds и policy buffer различаются. Строка «можно потратить» требует отдельного валидированного определения, а не `cash - reserve` во frontend.

### Home states

- Нет данных: один CTA «Import records» и вариант явно синтетического примера.
- Данные сомнительны: «Forecast needs review», конкретные причины и переход к ошибочным строкам. Не зелёная финансовая сводка.
- Дефицит: «Compare ways to cover the gap».
- Ждёт решения: «Review the next action» с количеством остальных, не approve-all.
- Идёт расчёт: уже полученные факты и статус фонового запуска, не заблокированный экран.
- UNKNOWN payment: «Checking payment status. Do not send again.» Без кнопки слепого повторного списания.
- Нет выявленной проблемы: «No gap in the selected scenario», с горизонтом/свежестью; не «бизнес в безопасности».

## 10. Основные пользовательские сценарии

### 10.1 Дефицит → решение

Home → case detail → варианты → review точного действия → timeline. Данные о проблеме и выбранных условиях сохраняются, пользователь не вводит их заново на каждом экране.

Case page включает: краткую причину; известное/неизвестное; сравнение baseline/plan; расходы; repayment tail; обязательные и stress scenarios; dependencies. Одно основное действие на состоянии, вторичные — спокойные ссылки.

Наличие base-feasible результата не превращает его в «Recommended» без явной цели и области проверки. «No new debt» при текущих сроках может быть недопустимым; «Supplier extension» — условным до подтверждения. Обе карточки полезны, но их нельзя выбрать как безусловно готовую оплату.

### 10.2 Подтверждение

Модальное окно/страница показывает действие человеческим языком, получателя, gross/net/fees по типу операции, валюту, due date, repayment, ожидаемое влияние на деньги, scope и ограничения. JSON/hash доступны в details.

Кнопка конкретна: «Approve loan draw · CNY 91,000», а не «Run action». Для платежа — название получателя и сумма. Представление проверяет, что операция именно выбранная пользователем. Закрытие диалога не равно отмене внешней операции.

После клика: approved → queued → sent → waiting for confirmation → reconciled. Показывать только фактически наблюдаемые переходы. «Reconciled» соответствует текущему completion predicate, не только ответу провайдера.

Сохранять exact approval на каждую требующую его команду. Нельзя получить удобство через отмену подтверждений или автоматическое разрешение всех шагов плана. Можно дать обзор всех шагов, но каждый consequential decision имеет свой scope.

### 10.3 Что изменилось

При новом факте показывать diff: какие суммы/даты/действия затронуты, почему прежний план изменился, какие approvals требуют обновления. Не заставлять искать отличия по двум длинным JSON.

### 10.4 Copilot

Панель знает открытый invoice/case/plan через серверно проверенные refs. Примеры запросов относятся к этому объекту: «Почему здесь дефицит?», «Что будет, если этот покупатель опоздает?», «Покажи комиссии».

Сверху краткий ответ, затем структурированная result card, источник и следующий шаг. Длинный tool trace — в раскрываемой диагностике. Постоянно виден реальный режим модели, но runtime technical metadata уходит в Settings.

Во время анализа показывать реальные этапы, time elapsed и возможность уйти со страницы. Cancel analysis не обещает отменить уже отправленный финансовый шаг; это две разные команды.

При timeout остаются доступными реальные завершённые вычисления. Нельзя изображать шаблонный текст как LIVE-генерацию.

### 10.5 Сессия

[REPORT] Membership token хранится в памяти страницы; refresh требует нового входа (R §6).

Сделать серверную сессию с ограниченным сроком и revocation. Для публичного deployment — HttpOnly/Secure cookie под HTTPS, SameSite и CSRF/origin защита мутаций; loopback dev имеет отдельную явно описанную конфигурацию. Не переносить bearer в localStorage. Смена роли должна действовать на дальнейшие запросы и approvals. Не подменять auth автоматическим OWNER-входом.

## 12. API для UX без дублирования домена

Сначала инвентаризировать текущие endpoints и модели; не добавлять несовместимый dispatcher рядом.

Небольшие read models: HomeSummary (position, issues, next actions, freshness); CaseDetail (scenario, alternatives, evidence, current action); ActionReview (exact payload projection); Timeline (ordered persisted events). Во всех — версия, as_of, computed_at, ACL-filtered refs и понятные block reasons.

Логика balances/approval/eligibility живёт в прежних сервисах. Frontend не решает, что можно отправить. `allowed_actions` — удобство отображения, сервер повторно проверяет их при мутации.

Обновления: начать с корректного polling сохранённого workflow, затем SSE по необходимости. Events содержат monotonic cursor/ID, scope и safe data. Поддержать reconnect/dedup и revocation. Прогресс вычисляется из фактических стадий, не из таймера «90%».

API/DTO типизировать последовательно. Error mapping: code → human label → причина → разрешённое восстановление. Наличие retryable=true не означает, что надо повторно создать финансовую команду с новым ключом.

## 14. Как проверять, что дизайн стал удобным

Минимальные задания без подсказок разработчика:
1. Понять, хватает ли денег до ближайшего обязательства, и назвать дату/сумму проблемы.
2. Найти причину и перейти к исходному документу.
3. Сравнить способы решения и объяснить разницу net proceeds/total cost/repayment.
4. Подготовить ровно одно действие и правильно назвать его получателя/сумму/последствие.
5. Понять UNKNOWN и не отправить вторую оплату.
6. Изменить сценарий одного поступления и подтвердить, что фактические данные не изменились.
7. Найти и исправить проблемную строку импорта.

Проектные цели: ≥4 из 5 участников завершают основные задания без пошагового сопровождения; все участники различают «запрос отправлен» и «оплата сверена». Это qualitative release gate, не статистическое доказательство удобства для рынка. Нужны участники, близкие к владельцам/бухгалтерам, а не только разработчики проекта.

Browser sizes: 1440×900, 1366×768, 768×1024, 390×844; keyboard/200% zoom; большой китайский контрагент, длинные суммы/названия, отсутствие данных, плохая сеть, истёкшая сессия, stale approval, paused graph. Проверять не только screenshots, но и клики/данные/сетевые ответы/финальный world. Трассы содержат потенциально чувствительные headers; применять тестовые секреты, проверку утечек и безопасное хранение.

LIVE метрики: сохранить прежние 20 кейсов и их исходный grader для сравнения; добавить новые авторизованные execution-задачи и парафразы на EN/ZH/RU с заранее фиксированным holdout. Считать отдельно tool/result/evidence/narrative/execution/latency и end-to-end success. Повторять в разрешённом бюджете; отсутствие прогона = NOT_RUN, а не приблизительный PASS. Не уменьшать защиту ради score.

## 15. Что показывать на конкурсе

Основная демонстрация — один непрерывный пользовательский путь в реальном кабинете: новые/изменённые исходные данные → фактический разрыв → живое объяснение и расчёты → варианты → осознанное exact approval → worker/sandbox → потерянный ответ и восстановление → сверенный результат. Отдельно показать честный неподходящий продукт, условную отсрочку и остановку неподтверждённого действия.

Не заменять этот путь записанной анимацией. Видео/скриншоты — доказательства проведённого запуска, не само выполнение. Дизайн-прототип из пакета нельзя включать как будто это работающая версия API.
